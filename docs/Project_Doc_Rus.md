## Фреймворк для сквозного тестирования — Документация проекта

### Введение

Этот проект реализует фреймворк для автоматизированного тестирования веб-приложений.

Основная цель проекта — разработка многократно используемой среды, упрощающей создание, выполнение и анализ сквозных тестов.

Фреймворк строится как полноценная программная система. В его основе лежит разделение тестовой логики, компонент пользовательского интерфейса, конфигурации, инфраструктуры запуска и отчетности.

Основные задачи среды тестирования:

- автоматизированное тестирование пользовательского интерфейса
- автоматизированное тестирование API
- работа с локальным и внешним веб-приложением
- контейнеризированная среда выполнения
- управление конфигурацией с использованием профилей YAML
- интеграция с CI/CD
- отчетность о тестировании и анализ результатов

Фреймворк реализован с использованием Python и современных инструментов автоматизации тестирования.

## Архитектура

Архитектура фреймворка построена как многоуровневая система, в которой тестовый слой, слой абстракции интерфейса, ядро и инфраструктура разделены по ответственности.

![Архитектурная диаграмма](diagrams/ArchSys.drawio.png)
*Рисунок 1. Многослойная архитектура фреймворка*

### Основные элементы архитектуры

Система включает четыре логических уровня:

1. **Тестовый слой**  
   Здесь находятся бизнес-сценарии, написанные на Pytest.  
   На этом уровне описывается логика проверок, а не технические детали работы с браузером.

2. **Слой абстракции интерфейса**  
   Этот слой содержит Page Object Model, компоненты пользовательского интерфейса и локаторы.  
   Он служит связующим звеном между тестами и тестируемым приложением.

3. **Слой ядра и конфигурации**  
   Сюда входят BrowserFactory, ConfigReader и вспомогательные механизмы работы с браузером и настройками.  
   Конфигурация задается через YAML-профили, что позволяет использовать разные окружения без изменения исходного кода тестов.

4. **Слой логирования и отчетности**  
   Здесь собираются логи, скриншоты и артефакты тестирования, после чего формируются отчеты Allure.

Отдельно в архитектуре выделяются объекты тестирования:

- локальное веб-приложение
- внешний веб-ресурс

## Подсистема компонентов

После описания общей архитектуры система декомпозируется на функциональные подсистемы.

![Диаграмма компонентов фреймворка](diagrams/DiagComp.png)  
*Рисунок 2. Диаграмма компонентов*

### Основные подсистемы

1. **Подсистема визуального моделирования**  
   Включает Page Object Model, компоненты интерфейса и локаторы.

2. **Подсистема управления сессиями браузера и конфигурацией**  
   Отвечает за YAML-профили, ConfigReader и BrowserFactory.

3. **Подсистема выполнения проверок**  
   Содержит тестовый движок и API-клиент, обеспечивая поддержку UI- и API-тестирования.

4. **Подсистема телеметрии**  
   Объединяет логирование и Allure-репортер.

### Назначение компонентов

- **Page Objects** скрывают детали работы с DOM и представляют страницы в виде объектов.
- **Locators** хранят селекторы отдельно от тестовой логики.
- **UI Components** позволяют переиспользовать часто встречающиеся элементы интерфейса.
- **ConfigReader** загружает параметры запуска из YAML.
- **BrowserFactory** создает и настраивает браузерную сессию.
- **API Client** отвечает за HTTP-запросы и проверку серверной логики.
- **Logger** фиксирует ход выполнения тестов.
- **Allure Reporter** формирует наглядный отчет по результатам прогонов.

## Page Object Model

Для взаимодействия с пользовательским интерфейсом используется шаблон Page Object Model.

![Архитектура POM](diagrams/POM.drawio.png)
*Рисунок 3. Архитектура Page Object Model*

### Как устроен POM

- **Локаторы** выносятся в отдельные классы и хранятся централизованно.
- **Base Page** содержит общие низкоуровневые действия с браузером.
- **Классы страниц** наследуют базовую страницу и реализуют пользовательские сценарии.
- **UI Components** используются как отдельные переиспользуемые блоки интерфейса.

### Что дает такой подход

- сокращает дублирование кода
- упрощает поддержку тестов
- делает сценарии более читаемыми
- снижает зависимость от изменений DOM-дерева
- позволяет собирать страницы из готовых элементов

## Управление браузером и конфигурацией

Фреймворк использует конфигурацию как данные.  
Параметры запуска задаются отдельно от кода тестов, что делает систему более гибкой и удобной для разных окружений.

### YAML-конфигурация

В YAML-профилях задаются:

- базовый URL
- тип браузера
- режим запуска
- размеры окна
- глобальные таймауты
- параметры окружения

Примеры профилей:

- `demoapp.local.yaml`
- `demoapp.docker.yaml`
- `demoqa.local.yaml`

### Роль ConfigReader

`ConfigReader` загружает нужный профиль, проверяет параметры и передает их дальше в систему запуска.

### Роль BrowserFactory

`BrowserFactory` создает изолированный браузерный контекст на основе конфигурации.  
Это позволяет запускать каждый тест в чистой сессии без влияния предыдущих прогонов.

## Поддержка UI и API тестирования

Фреймворк построен как гибридное решение и поддерживает два типа проверок:

### UI-тесты

UI-тесты проверяют:

- корректность отображения страниц
- поведение интерфейса
- работу форм и элементов управления
- пользовательские сценарии в браузере

### API-тесты

API-тесты проверяют:

- ответы серверной части
- структуру данных
- статус-коды
- корректность бизнес-логики на уровне backend

## Логирование и отчетность

Во время выполнения тестов фреймворк собирает артефакты, которые помогают анализировать результаты и причины ошибок.

### Что сохраняется

- логи выполнения
- скриншоты при падении тестов
- дополнительные вложения
- данные для Allure-отчетов

---

## Выполнение тестов

Тесты выполняются с помощью Pytest.

Примеры:

```
pytest -k api -s -m app_demoapp --config=demoapp.local.yaml
pytest -m app_demoapp --config=demoapp.local.yaml
```

## Интеграция с Docker

Тестовая среда поддерживает запуск в контейнерах Docker.

![Диаграмма развёртывания](diagrams/Docker.drawio.png)
*Рисунок 4. Схема контейнеризированной инфраструктуры*

Что показывает схема

- Test Runner запускает тесты внутри контейнера
- локальное приложение поднимается как отдельный сервис
- внешний веб-ресурс тестируется через отдельный вектор запуска
- артефакты сохраняются в папки логов и отчетов
- конфигурация передается через переменную CONFIG_FILE

Зачем это нужно

- одинаковые условия запуска
- изоляция окружения
- повторяемость результатов
- упрощение переноса между машинами
- подготовка к интеграции в CI/CD

Примеры команд: 

```
docker compose build
docker compose up -d demo-app
docker compose up e2e-demoapp
docker compose up e2e-demoqa
```
